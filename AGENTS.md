# Fobles Workspace Instructions

## Source And Runtime

- TypeScript source of truth: `src/`. There is no longer a `src/extension/` wrapper, `src/features/`, or `src/styles/` — every surface is a direct child of `src/` (see architecture below).
- Runtime unpacked extension: `dist/unpacked/`.
- Do not edit generated `dist/unpacked/content.js`, `dist/unpacked/background.js`, `dist/unpacked/options.js`, `dist/unpacked/popup.js`, or `dist/unpacked/fobles.css` directly.
- `src/public/` holds static files copied as-is into `dist/unpacked/` (maintained, hand-editable): `manifest.json`, `options.html`, `popup.html`, `fobles_icon.png`.
- `src/buildInfo.ts` is auto-generated by `tools/scripts/build/write-build-info.js`; currently unused (dead code) — don't hand-edit it.
- Extension architecture is four independent surfaces, each its own esbuild entry, plus a `shared/` folder for genuinely cross-surface code:
  - `src/content/` — code injected into the Sitecore page (content script). Entry `content/index.ts` bundles to `dist/unpacked/content.js`. Internally split by role, not by feature:
    - `content/toolbar/` — renders/wires everything that lives inside `.fobles-toolbar-container` (the floating draggable widget): the container/grip/close button, plus `toolbar/quick-menu/` and `toolbar/proxy-buttons.ts` (the popups' DOM-building and visibility state). Toolbar may depend on `features/augmentor/`; the reverse is never allowed.
    - `content/features/augmentor/` — all code that temporarily manipulates the real Sitecore page/UI (adds buttons to fields and the tree, hides Sitecore elements, proxies clicks to the ribbon). Renamed from `fobles/` — the rename is organizational only; the `FOBLES` const, `fobles-*` CSS classes, and the user-facing "Fobles" feature name are unchanged.
    - `content/features/quick-menu/` — deferred anomaly: `kick-users.ts`/`ai-pages.ts` are command logic that hasn't been moved into `augmentor/` yet (see `docs/TODO.md`).
    - `content/styles/` (Sass), `content/guard.ts` (the eligibility "gateway" deciding whether toolbar/augmentor should run at all — a separate concern from both), and other top-level `content/` utilities.
  - `src/background/` — MV3 service worker. Entry `background/index.ts` bundles to `dist/unpacked/background.js`.
  - `src/options/` — "Additional Settings" page logic. Entry `options/index.ts` bundles to `dist/unpacked/options.js`.
  - `src/popup/` — toolbar-icon popup logic. Entry `popup/index.ts` bundles to `dist/unpacked/popup.js`.
  - `src/shared/` — code used by more than one surface (e.g. `constants.ts`'s `STORAGE`/`MESSAGE`/`LOGGER`, and `shared/quick-menu/` — button catalog/settings/ids/`menu-groups.ts`/`menu.types.ts` — consumed by both `content/toolbar/` and `options/`). Never let `content/`-only code (e.g. anything touching the live Sitecore DOM) leak into `shared/`.
  - `src/shared/storage/` — the only code allowed to touch `chrome.storage` directly: a domain-agnostic facade (`getStorageValue`/`setStorageValue`/`onStorageChange`/`getAllStorageValues` in `storage.ts`) plus typed accessors per storage key (`debug-settings.ts`, `nav-settings.ts`, `toolbar-placement.ts`, `ai-pages-mappings.ts`, `fobles-state.ts` for the separate `localStorage`-based `FOBLES_STATE`). The facade knows nothing about quick-menu, buttons, or any other domain — domain-specific storage (e.g. `shared/quick-menu/button-settings.ts`) calls into the facade rather than touching `chrome.storage` itself.
- Use `fobles` terminology for the active extension.
- Always use "fobles"/"Fobles" (plural); never use the singular "foble"/"Foble" anywhere, including identifiers, file names, CSS classes, data attributes, and prose.

## Code Conventions

- Prefer `type` over `interface` for TypeScript type definitions.
- Put shared types/interfaces in a dedicated `x.types.ts` file, not inline in a logic file.
- Put shared const data/config collections in their own dedicated const file, separate from the logic that consumes them.
- Prefer named `const`s over magic strings, especially for values reused more than once or that carry structural meaning (e.g. group titles).
- Prefer event handlers/listeners in a dedicated `handlers.ts` file, not mixed in with element-building or other logic in the same file.
- Order type/object fields with required fields first, then optional (`?`) fields, identity fields (`id`/`label`) leading within each group.
- `SITECORE` (`src/content/sitecore.ts`) holds every magic string/selector that Sitecore itself renders (its DOM classes/ids, paths, xmlcontrol names, query params). `FOBLES`/fobles-prefixed constants hold only strings the extension itself generates (its own injected classes, data attributes, UI copy). Never mix the two in the same const object.
- Prefer const object properties to be listed alphabetically.
- Prefer keeping code files under 314 lines; split into smaller dedicated files when a file grows past that.

## Build And Validation

- Run `npm run typecheck:extension` after TypeScript changes.
- Run `npm run build:scss` after stylesheet-only changes.
- Run `npm run build:extension` after extension changes. It regenerates runtime bundles and copies the extension icon.
- Run `npm run test:e2e:list` to verify Playwright test discovery.
- Generated test output is stored under `tests/test-artifacts/` and should not be committed.
- Reload the unpacked extension and hard-refresh (Ctrl+F5) affected Sitecore tabs after manifest or content-script changes. A normal refresh can leave the old content script running against an invalidated extension context, causing `chrome.storage` reads to silently fall back to defaults.

## Extension Behavior

- Browser Site Access controls are authoritative; do not add a custom domain allowlist or dynamic content-script registration.
- Content scripts are registered for HTTP/HTTPS pages and decide eligibility using `src/content/guard.ts`.
- Sitecore `default.aspx?xmlcontrol=...` pages must be explicitly allowlisted in `ALLOWED_XML_CONTROLS`.
- Preserve Sitecore layout when hiding an original control by using the existing Fobles spacer helpers.
- Fobles navigation targets the top-level tab for same-tab actions.

## Styling

- All Sass source now lives under `src/content/styles/` (content-only, since `fobles.css` is only loaded via `manifest.json`'s `content_scripts`).
- Content-editor field/tooltip/dialog styles: `_content-editor-fields.scss`.
- Content-editor tree-node fobles styles: `_content-editor-tree.scss`.
- Toolbar/quick-menu/proxy-buttons chrome styles: `_fobles-menu.scss`.
- Sass entry point (just `@use` statements): `fobles-extension.scss`.
- Generated runtime stylesheet: `dist/unpacked/fobles.css`.
- Read the current Sass file before editing because it may contain user changes.
